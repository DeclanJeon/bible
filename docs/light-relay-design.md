# 빛의 릴레이 설계 문서

> 말씀편지의 핵심 운영 모델. 사용자가 익명으로 고민을 보내면, 시스템이 성구를 추천하고 첫 릴레이 주자(시스템 제작자)가 답변한다. 답변을 받은 사용자는 카드뉴스와 함께 "다음 릴레이에 참여하시겠습니까?"를 제안받고, 수락하면 다른 사용자의 고민을 받고 답변하는 릴레이 주자가 된다. 빛은 끊기지 않는다. 여러 분기가 동시에 진행되는 메쉬 구조다.

## 1. 철학

### 1.1 핵심 원칙

> "내가 먼저 빛이 되어 사람들에게 본이 되어야 한다."

예수님의 사랑을 바탕으로, 시스템 제작자가 먼저 빛을 보여준다. 첫 번째 답변은 항상 시스템 제작자가 한다. 그 빛이 사용자에게 전달되고, 사용자가 그 빛을 이어받아 다음 사람에게 전달한다.

### 1.2 릴레이의 의미

- **순차 큐가 아니다.** 여러 분기가 동시에 진행되는 메쉬 구조다.
- **연결이 중요하다.** 한 사람이 받은 위로가 → 그 사람이 다음 사람에게 전달되는 연결.
- **빛이 끊기지 않는다.** 릴레이 참가자가 있는 한, 모든 고민에 답변이 도달한다.
- **선택이다.** 강제가 아니다. 답변을 받은 사용자가 자발적으로 릴레이를 이어간다.

## 2. 플로우

### 2.1 전체 플로우

```text
[사용자A] 고민 작성
    ↓
[시스템] 성경 컴패니언이 성구 추천
    ↓
[시스템] 시스템 제작자(declan@ponslink.com)에게 이메일 전달
    ↓
[시스템 제작자] 추천 성구 중 선택 + 답변 작성 → "보내기"
    ↓
[시스템] 고민 + 선택 성구 + 답변 → 카드뉴스 이미지 생성
    ↓
[시스템] 카드뉴스를 사용자A에게 이메일 전달
    ↓
[사용자A] 카드뉴스 수신 → "빛의 릴레이에 참여하시겠습니까?"
    ↓
  ┌─ 수락 → 릴레이 participant pool 등록 → 다른 사용자의 고민 수신 가능
  └─ 거절 → 릴레이 미참여, 필요시 설정에서 참여 가능
    ↓ (수락 시)
[사용자B] 고민 작성
    ↓
[시스템] 성구 추천 → 릴레이 pool에서 랜덤 1명 선택 (사용자A)
    ↓
[사용자A] 사용자B의 고민 이메일 수신 → 성구 선택 + 답변
    ↓
[시스템] 카드뉴스 생성 → 사용자B에게 전달
    ↓
[사용자B] "빛의 릴레이에 참여하시겠습니까?"
    ↓
  메쉬 확장: 사용자A, 사용자B 모두 릴레이 pool에 존재
  → 다음 고민은 pool에서 랜덤 선택
```

### 2.2 메쉬 구조

```text
사용자A 고민 → 제작자 응답 → 사용자A 릴레이 참가
사용자B 고민 → 사용자A 응답 → 사용자B 릴레이 참가
사용자C 고민 → 사용자B 응답 → 사용자C 릴레이 참가
사용자D 고민 → 제작자 응답 (사용자A가 바쁜 경우)
사용자E 고민 → 사용자C 응답
...
```

동시에 여러 분기가 돌아간다. 순서는 상관없다. 핵심은 **빛이 끊기지 않는 것**.

### 2.3 시스템 제작자 역할

- **첫 릴레이 주자**: 모든 새 편지의 첫 수신자는 시스템 제작자다.
- **영구 fallback**: 릴레이 pool이 비어있으면 시스템 제작자가 응답한다.
- **모범 제시**: 제작자가 먼저 위로하고 성구를 선택하는 모습을 보여준다.
- **고정 이메일**: `declan@ponslink.com`

## 3. 매칭 규칙

### 3.1 수신자 선택 로직

```text
새 편지가 들어오면:
1. 시스템 제작자(declan@ponslink.com)에게 항상 먼저 보냄
2. 제작자가 답변하면 → 유저에게 카드뉴스 전달 + "릴레이 참가?" 제안
3. 유저가 수락 → 릴레이 participant pool에 등록
4. 다음 새 편지가 들어오면 → 릴레이 pool에서 랜덤 1명 선택
5. 없으면 → env fallback (제작자)
```

### 3.2 랜덤 매칭 (큐 아님)

- 릴레이 pool에서 랜덤 1명 선택.
- 순서는 중요하지 않다. 연결이 중요하다.
- 같은 사람이 연속 선택되지 않도록 cooldown 적용 (기존 12h).
- 하루 cap 적용 (participant 설정값, 기본 3).

### 3.3 inactive 처리

- 릴레이 pool의 participant가 48시간 미응답 시 → 다음 사람으로 자동 스킵.
- pause/unsubscribed participant는 pool에서 제외.
- 작성자 본인은 자기 편지의 수신자에서 제외.

### 3.4 fallback 체계

```text
릴레이 pool에 eligible participant가 있음 → 랜덤 1명 선택
    ↓ (없음)
env fallback (LETTERS_RECIPIENT_EMAILS / PONSLINK_ADMIN_EMAILS)
    ↓ (없음)
시스템 제작자(declan@ponslink.com) 고정
```

## 4. 릴레이 참가 UX

### 4.1 참가 제안 시점

답변 카드뉴스를 수신한 직후. 카드뉴스를 보고 나서 "이 빛을 이어가시겠습니까?"를 제안한다.

### 4.2 참가 UI

```text
┌─────────────────────────────────────────────┐
│                                             │
│  [카드뉴스 이미지: 고민 + 성구 + 답변]       │
│                                             │
├─────────────────────────────────────────────┤
│                                             │
│  당신이 받은 이 빛을                         │
│  다음 사람에게 이어가시겠습니까?              │
│                                             │
│  릴레이에 참여하면, 다른 사람의 익명 고민을   │
│  받게 되고, 성구를 고르고 위로의 답변을       │
│  보낼 수 있습니다.                           │
│                                             │
│  [빛의 릴레이에 참여하기]  [지금은 괜찮습니다]│
│                                             │
│  언제든 설정에서 변경할 수 있습니다.          │
│                                             │
└─────────────────────────────────────────────┘
```

### 4.3 참가 후 상태

- `canReceiveLetters = true`
- 릴레이 pool에 등록
- 설정 페이지에서 "빛의 릴레이 참여" on/off 가능
- 다음 편지가 들어오면 랜덤 매칭 후보

### 4.4 거절 후 재참여

- `/letters/settings`에서 언제든 토글 가능.
- `/letters/join`에서 처음 가입할 때도 선택 가능.

## 6. UI/UX 수정 사항

### 6.1 랜딩 페이지 (`/letters`)

현재:
```

```

하이라이트:
- "빛의 릴레이" 개념 소개
- 첫 릴레이 주자는 시스템 제작자임을 자연스럽게 전달
- flow 설명: 고민 → 성구 추천 → 릴레이 주자가 답장 → 카드뉴스 전달

### 6.2 가입 페이지 (`/letters/join`)

```
"다른 사람의 익명 말씀편지를 받고 답장하기"
```

```
"빛의 릴레이에 참여하기"
"당신이 받은 위로를 다음 고민자에게 전달합니다."
```

### 6.3 발송 완료 페이지 (`/letters/sent`)

현재:

### 6.5 설정 페이지 (`/letters/settings`)


- "이 성구로 답변하기" 버튼 → 답변 폼으로 이동
- 또는 이메일 내 간결한 답변 CTA

### 6.7 카드뉴스 구성

- 릴레이 주자의 답변
- 시각적 조합 (하나의 카드에 통합 또는 병렬 배치)

## 7. 백엔드 수정 사항

### 7.1 시스템 제작자 상수

```typescript
// lib/letters.ts
const SYSTEM_CREATOR_EMAIL = "declan@ponslink.com";
```

### 7.2 첫 편지 수신 로직

```typescript
function pickRecipient(data, authorEmail, locale) {
  // 랜덤 매칭 (기존 유지)
  // 다만 시스템 제작자가 항상 fallback 최우선
}
```

기존 랜덤 매칭을 유지하되:
1. 시스템 제작자가 항상 fallback 최우선.
2. 릴레이 pool에서 랜덤 1명 선택.
3. 없으면 env fallback → 시스템 제작자.

### 7.3 카드뉴스 생성 → 전달 순서

현재:
```
답변 제출 → 답변 카드 생성 → 이미지 생성 (async fire-and-forget) → 이메일 발송
```

수정:
```
답변 제출 → 답변 카드 생성 → 이미지 생성 (await) → 카드뉴스 포함 이메일 발송
```

핵심: 이미지 생성 완료 후 이메일을 발송해야 카드뉴스가 이메일에 포함된다.

### 7.4 릴레이 참가 API

```typescript
// POST /api/letters/participants/relay-accept
// body: { answerId: string }
// → canReceiveLetters = true
// → participant pool 등록
```

### 7.5 이메일 내 답변 UX

기존 reply/[token] 페이지를 유지하되, 이메일 CTA를 강화:
- 추천 성구를 이메일에 직접 표시
- "이 성구로 답변하기" 버튼 → reply/[token] 페이지로 이동 (성구 자동 선택)

## 8. 운영 규칙

### 8.1 시스템 제작자

- 이메일: `syas0301@gmail.com` (고정 테스트/마스터 릴레이)
- 역할: 첫 릴레이 주자 + 영구 fallback
- 작성자 본인은 수신 후보에서 제외하며, 닉네임을 비우면 귀여운 임의 닉네임을 자동 지정

### 8.2 릴레이 pool 관리

- 참가: 답변 수신 후 자발적 선택
- 탈퇴: 설정 페이지에서 언제든 가능
- pause: 설정에서 7일/30일 pause
- cap: 하루 최대 수신 (설정값, 기본 3)

### 8.3 inactive timeout

- 릴레이 pool participant가 48시간 미응답 → 자동 스킵
- 스킵 후 다음 랜덤 participant에게 전달
- 스킵된 participant는 pool에서 제거되지 않음 (다음 기회에 다시 선택 가능)

### 8.4 안전장치

- crisis 감지 시 → 랜덤 발송 안 함, 도움 안내 표시
- contact info 차단 (이메일, 전화번호, 카카오톡 등)
- 신고 기능 유지
- 작성자/수신자 이메일 상호 비공개
